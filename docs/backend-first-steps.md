# Beauty Room: первый шаг в бэкенд

На этом этапе подготовлена структура PostgreSQL и подключение Prisma внутри Next.js.
Публичный сайт пока читает существующие файлы процедур. Кабинет владельца,
авторизация, API клиентов и загрузка фотографий — следующие этапы.

## 1. Что происходит на сервере

Браузер показывает интерфейс. Сервер принимает запрос, проверяет права пользователя,
проверяет данные и выполняет запрос к базе. База хранит записи между перезапусками.
Серверный модуль `src/server/db/client.ts` помечен `server-only`:
Next.js не позволит импортировать его в клиентский компонент.
Сама эта пометка не заменяет авторизацию: её добавим перед подключением данных клиентов к интерфейсу.

Prisma переводит запросы TypeScript в SQL и генерирует типы по нашей схеме.
Например, `db.client.create(...)` сохраняет запись, а `db.client.findUnique(...)`
читает её по уникальному идентификатору.

## 2. Создай учебную базу в Neon

1. Открой https://console.neon.tech/ и создай проект `beauty-room-dev`.
2. Используй его только для обучения с вымышленными клиентами.
3. В окне **Connect** выбери базу и пользователя. С включённым **Connection pooling**
   скопируй PostgreSQL connection string для `DATABASE_URL`.
4. Выключи **Connection pooling** и скопируй прямую строку для `DIRECT_URL`.
5. В корне проекта открой существующий `.env.local` и добавь две переменные:

```dotenv
DATABASE_URL="сюда вставь pooled connection string из Neon"
DIRECT_URL="сюда вставь direct connection string из Neon"
```

Это шаблон, а не рабочие адреса. Строки включают пароль: не отправляй их в чат,
не добавляй в Git и не используй префикс `NEXT_PUBLIC_`. Сохрани параметры SSL,
которые Neon добавил в адрес. Не перезаписывай остальные переменные `.env.local`.

Next.js загружает `.env.local` сам. Команды Prisma и учебные скрипты также
загружают его, затем `.env`; переменные окружения процесса имеют приоритет.
Если позже добавишь эти переменные в Vercel, выбирай нужное окружение:
учебная база не должна случайно стать базой реальных клиентов.

## 3. Создай таблицы

Из корня проекта выполни:

```sh
npm run db:validate
npm run db:generate
npm run db:deploy
npm run db:check
```

- `validate` проверяет описание таблиц.
- `generate` создаёт TypeScript-клиент для работы с ними. Команда не создаёт таблицы.
- `deploy` применяет сохранённую SQL-миграцию к выбранной базе.
- `check` проверяет соединение и наличие таблицы клиентов, не выводя их данные.

Для этого проекта используем Node.js 22.12+ в ветке 22 LTS или совместимую LTS-версию.
Первую миграцию применяй к отдельной новой учебной базе. В ней есть `CREATE TABLE`;
она не предназначена для существующей базы с чужой структурой.

**Миграция** — сохранённый файл изменений структуры базы.
`prisma/schema.prisma` описывает желаемую структуру, а
`prisma/migrations/20261005090000_init/migration.sql` создаёт её в PostgreSQL.
Prisma отмечает выполненные миграции в служебной таблице и не применяет их повторно.

При дальнейших изменениях учебной схемы используй:

```sh
npm run db:migrate -- --name имя_изменения
```

`migrate dev` предназначен для разработки и может предложить сброс базы при
конфликте схем. Не запускай его на базе с реальными клиентами. Для применения уже
проверенных миграций используется `db:deploy`.

## 4. Первое упражнение: создать и прочитать клиента

```sh
npm run db:lesson
```

Открой `scripts/database/lesson.ts` и сопоставь код с результатом:

1. `create` создаёт вымышленного клиента и связанную контактную ссылку.
2. `findUniqueOrThrow` читает этого клиента по `id`, включая контакты.
3. Всё выполняется в транзакции — группе запросов, которые применяются целиком
   или отменяются целиком.
4. В конце специально выбрасывается ошибка: транзакция откатывается,
   поэтому учебные записи не остаются в базе. Остальные записи не затрагиваются.

После запуска увидишь сообщение о создании/чтении клиента и об отмене транзакции.
Это первый проверяемый путь «TypeScript → PostgreSQL → TypeScript».
Скрипт запускается из терминала; доступа к данным клиентов через сайт пока нет.

Чтобы вручную посмотреть таблицы, запусти:

```sh
npm run db:studio
```

Это инструмент разработчика, а не будущий кабинет владельца. Можно создать
вымышленного клиента в таблице `Client`, обновить страницу Studio и увидеть,
что запись сохранилась. Телефон храним строкой: знак `+` и начальные нули значимы.
В будущем форма будет нормализовать и проверять номер перед сохранением.

## 5. Как устроены связи

| Таблица | Зачем нужна |
| --- | --- |
| `Client` | Имя, фамилия, телефон и дата архивирования клиента |
| `ClientContact` | Несколько контактных ссылок одного клиента |
| `Treatment` | Общие параметры процедуры: цена, длительность, публикация |
| `TreatmentTranslation` | Тексты одной процедуры на `he`, `en`, `ru` |
| `TreatmentRecord` | Один факт выполнения процедуры конкретному клиенту |
| `Media` | Адреса публичных фотографий сайта и порядок отображения |

`id` — уникальный идентификатор записи. `clientId` в контакте и истории указывает
на конкретного клиента, `treatmentId` — на процедуру. PostgreSQL проверяет,
что связанные записи действительно существуют.

У одной процедуры может быть только один перевод на каждый язык:
это ограничение `@@unique([treatmentId, locale])`.
Списки этапов и проблем кожи пока хранятся в JSON, чтобы сохранить текущую
структуру контента. В будущем сервер будет проверять форму этих данных.

История хранит название процедуры и фактически уплаченную цену на момент посещения.
Изменение публичного названия или цены не переписывает историю.
Клиента или процедуру с историей нельзя просто удалить: используем архивирование.
Даты посещений хранятся как `timestamptz`; интерфейс будет показывать их
в часовом поясе `Asia/Jerusalem`.

Файлы фотографий позже загрузим в объектное хранилище. `Media` хранит ссылки,
а не содержимое JPEG. Таблица предназначена для публичного контента сайта;
частные фотографии клиентов потребуют отдельной модели доступа.

## 6. Что делаем следующим

После успешных `db:check` и `db:lesson` добавляем вход владельца и защищённый
доступ к данным. Затем строим форму создания клиента, список и историю посещений.
После этого переносим тексты и фотографии процедур из файлов в базу и подключаем
редактор с черновиками и публикацией. Учётную запись владельца свяжем с выбранным
механизмом авторизации на этом этапе, вместо самостоятельного хранения паролей.

## Что проверено при подготовке

Схема Prisma, генерация клиента, TypeScript, ESLint и production-сборка проходят.
Начальная SQL-миграция проверена в локальном PostgreSQL runtime PGlite:
создание таблиц, уникальность переводов, защита истории от удаления,
сохранение фактической цены, откат транзакции и связи контактов/фотографий.
Это не проверка облачного соединения: миграция в Neon и учебный Prisma-скрипт
будут проверены после добавления строк подключения.

`npm audit` сообщает 9 high-записей: 5 уже были в цепочке ESLint, ещё 4 относятся
к транзитивным зависимостям Prisma CLI (`deepmerge-ts`, `mysql2` и их родителям).
Драйвер MySQL в этом проекте не используется. Перед выпуском CRM следует
повторно проверить исправления в совместимых версиях; автоматический
`npm audit fix --force` предлагает смену основных версий и не применялся.
